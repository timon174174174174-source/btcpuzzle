# Сохранение и возобновление прогресса сканирования

- **Дата:** 2026-06-07
- **Статус:** Утверждён дизайн, ожидает план реализации
- **Ветка:** `feature/save-resume-progress`
- **Контрибуция:** репозиторий апстримный (не наш). Изменения готовятся как PR-предложение. Внутренняя спека (этот файл) в апстрим-PR не включается.

## 1. Контекст и проблема

Клиент `btcpuzzle.info` (форк VanitySearch с пул-режимом) сканирует на GPU диапазоны
приватных ключей, выданные пулом. Главный цикл — [main.cpp:695](../../../main.cpp):
запросить диапазон → построить keyspace `[ksStart, ksFinish]` → `VanitySearch::Search()`
сканирует → собрать proof-ключи → `submitRange()` → повторить.

Если процесс закрывается посреди сканирования диапазона (reboot, power-loss, `docker stop`,
Ctrl+C), весь прогресс по текущему диапазону теряется: при следующем старте всё начинается
заново.

### Что уже есть (нерабочая заготовка)
От апстрима остались следы механизма сохранения, но он мёртвый:
- `VanitySearch::saveProgress()` ([Vanity.cpp:1030](../../../Vanity.cpp)) — считает минимальный
  ключ в памяти, **на диск ничего не пишет**.
- Единственный её вызов **закомментирован** ([Vanity.cpp:1141](../../../Vanity.cpp)).
- Поле `TH_PARAM::THnextKey` выставляется один раз перед стартом потока
  ([Vanity.cpp:1076](../../../Vanity.cpp)) и **никогда не обновляется** во время скана.

Рабочего сохранения/возобновления нет.

## 2. Ключевое ограничение и выбранная стратегия

Конкретный диапазон выдаёт **сервер пула** (`GET /puzzle/N/range`,
[PoolClient.cpp:378](../../../Pool/PoolClient.cpp)). У эндпоинта нет параметра «продолжить
с позиции X». На перезапуске пул выдаёт **новый** диапазон (подтверждено пользователем).
Поэтому «сохранить позицию и попросить тот же диапазон» невозможно.

**Выбранная стратегия — «доделать прерванный диапазон + сабмит»:** при старте, *до* запроса
нового диапазона, клиент досканирует сохранённый диапазон с последней позиции, соберёт
proof-ключи и засабмитит их в пул, затем удалит чекпойнт и продолжит обычную работу. Так
клиент остаётся в пуле, а до-крашевая GPU-работа не пропадает — при условии, что пул ещё
примет этот диапазон.

## 3. Цели и не-цели

**Цели:**
- Переживать жёсткое завершение процесса (не только штатное закрытие).
- При старте докатывать незавершённый диапазон и сабмитить его.
- Не терять уже найденные proof-ключи.
- Не ломать существующую пул-логику и приватность untrusted-режима.

**Не-цели:**
- Возобновление того же *пул-диапазона* через сервер (невозможно).
- Solo/локальный режим сканирования вне пула.
- Многократный параллельный GPU в одном процессе (клиент — один GPU на инстанс).

## 4. Архитектура решения

### 4.1. Расчёт позиции (offset)
GPU делит `[ksStart, ksFinish]` на `N = numThreadsGPU` равных подотрезков; поток `i` владеет
`[s_i, s_{i+1})`, где `s_i = ksStart + i·D`, `D = (ksFinish − ksStart) / N`. Все потоки идут
синхронно шагом `STEP_SIZE`. После `L` запусков:
- `counters[0] = L · STEP_SIZE · N` (уже считается в коде),
- продвижение каждого потока `offset = L · STEP_SIZE = counters[0] / N` — **деление точное**
  (counters[0] всегда кратно `N`).

`offset` — единственное число, описывающее прогресс по диапазону.

Допущение: один GPU на инстанс (`numGPUs == 1`), что соответствует дизайну клиента
(README: "Only one GPU per instance"). Используем `counters[0]` и `N` от устройства 0.

### 4.2. Формат чекпойнта
Файл `progress/checkpoint_gpu<gpuIndex>.txt`, простой текст `key=value` (без JSON-либы, в
стиле существующего кода). Запись **атомарная**: писать во временный файл и `rename()`,
чтобы краш во время записи не оставил битый чекпойнт.

Поля:
- `puzzle` — целевой puzzle (для защиты от рассинхрона с конфигом).
- `hex`, `rangeStart`, `rangeEnd`, `targetAddress` — восстановить keyspace.
- `proofAddresses` — список proof-адресов (для файла адресов VanitySearch).
- `numThreads` — `N` на момент сохранения (валидация геометрии при resume).
- `offset` — позиция (hex-строка Int).
- `foundProof` — пары `адрес=приватник` для уже найденных proof-адресов.

**Целевой приватный ключ не записывается никогда.** В чекпойнте хранятся только proof-адреса;
нашли целевой ключ → диапазон завершён, возобновлять нечего. Это сохраняет смысл
untrusted-режима (защита именно целевого ключа). Proof-ключи и так уходят в пул и уже могут
попадать на диск (`FLAG_ERROR_*`, [main.cpp:909](../../../main.cpp)), поэтому их сохранение
ничего нового не раскрывает.

### 4.3. Когда сохраняем
- Периодически из мониторящего цикла `Search()` (раз в ~5 с).
- Дополнительно — сразу при каждом найденном proof-ключе (редки, терять нельзя).
- Снимок `offset` и `foundProof` берётся согласованно: к моменту, когда `counters[0]`
  отражает скан до позиции `offset`, все proof-ключи из `[.., offset)` уже добавлены в
  `foundKeys` (в `FindKeyGPU` обработка попаданий идёт до инкремента `counters`). Значение
  `offset` никогда не оказывается «впереди» сохранённых ключей — это гарантирует отсутствие
  пропусков при resume.

### 4.4. Поток возобновления (при старте, до `getRange()`)
1. Если `save_progress` выключен или файла нет — обычный цикл.
2. Прочитать чекпойнт. Если `puzzle`/`targetAddress` не совпадают с текущим конфигом —
   удалить и идти в обычный цикл.
3. Восстановить keyspace из `hex`/`rangeStart`/`rangeEnd`; восстановить файл адресов из
   `proofAddresses` + `targetAddress`; проиграть `foundProof` через `client.onKeyFound()`.
4. Запустить скан остатка:
   - **`numThreads` совпадает с текущим `N`:** сдвинуть старт каждого потока на `offset` →
     досканировать ровно `∪[s_i+offset, s_{i+1})`. Условие конца цикла
     (`firstGPUThreadLastPrivateKey = ksStart + D`) не меняется. Восстановленные ключи (из
     части до краша) + новонайденные = полный набор. Без дыр и переска́на.
   - **`numThreads` не совпадает:** безопасный откат — скан всего `[ksStart, ksFinish]`
     заново (offset игнорируется); проигранные ключи просто ускоряют/дополняют набор.
     Теряется только до-крашевая работа, корректность гарантирована.
5. После скана: если `hasAllProofKeys()` — сабмит (см. 4.6). Удалить чекпойнт. Перейти к
   обычному циклу.

### 4.5. Интеграция со сканером
- В `getGPUStartingKeysMT()` добавить параметр стартового `offset` (Int), прибавляемый к
  старту каждого потока перед вычислением публичного ключа. `firstGPUThreadLastPrivateKey`
  остаётся `ksStart + D`.
- В `FindKeyGPU()` сохранить `numThreadsGPU` в член класса для мониторинга.
- В `Search()` мониторящий цикл вызывает новый **progress-callback** (симметрично
  `keyCallback`) с текущими `offset` и `N`. Лямбда в `main.cpp` строит и пишет чекпойнт из
  `rangeData` + найденных proof-ключей. Развязывает `VanitySearch` от пул-специфики.

### 4.55. Конкурентность доступа к `foundKeys`
Периодическое сохранение идёт из **мониторящего потока** `Search()`, а `foundKeys`
наполняется из **GPU-потока** (`checkAddr` → `keyCallback` → `onKeyFound`). Это вводит
конкурентный доступ к `std::map foundKeys`, которого в текущем коде нет (его читают только
после завершения `Search()`). Нужен `std::mutex` в `PoolClient`, под которым работают
`onKeyFound`, `hasAllProofKeys`, `getProofKeys` и новый аксессор пар. Без него — UB/гонка.

### 4.6. Сабмит дослеженного диапазона
Ограниченное число попыток (например, 3). При успехе или явном отказе пула (диапазон уже
занят/завершён) — удалить чекпойнт и идти за новым диапазоном. При неустранимой ошибке —
бэкап proof-ключей в `FLAG_ERROR_*` (как сейчас), удалить чекпойнт, продолжить. **Без вечного
цикла** (в отличие от текущего `while(!submitted)` в [main.cpp:898](../../../main.cpp)).

### 4.7. Конфигурация
- `pool.conf`: `save_progress=true|false` (по умолчанию **true**).
- Аргумент CLI: `-saveprogress true|false`.
- Docker: build/run-arg `SAVE_PROGRESS`.
- Парсинг в `PoolConfig::loadFromFile`, поле `bool saveProgress = true`, вывод в шапке.

## 6. Граничные случаи
- **Пул отверг диапазон** (занят/завершён): bounded retry → бэкап `FLAG_ERROR_*` → удалить
  чекпойнт → новый диапазон.
- **Чекпойнт от другого puzzle/таргета:** игнорировать и удалить.
- **`numThreads` сменился** (другая GPU/grid): полный рескан диапазона (без потери
  корректности).
- **`save_progress=false`:** ничего не пишем; существующий чекпойнт не трогаем.
- **Битый/частичный файл:** атомарная запись это предотвращает; при ошибке чтения — удалить
  и идти в обычный цикл.

## 7. Тестирование и верификация
GPU в среде разработки недоступен, поэтому:
- **Юнит-тесты модуля `Checkpoint`** (без GPU): round-trip сериализации, отсутствующий файл,
  битый файл, атомарность записи (temp + rename), несовпадение puzzle/таргета.
- **Тест арифметики партиций на `Int`** (без GPU): проверка `offset = counters/N`, формул
  `s_i` и `s_i+offset`, что объединение `[s_i, s_i+offset) ∪ [s_i+offset, s_{i+1})` покрывает
  диапазон без дыр.
- **Сборка проекта** (компиляция).
- **Полный GPU-прогон — на стороне пользователя.** Инструкция проверки: запустить на puzzle 38,
  прервать процесс на середине, перезапустить, убедиться по логам, что диапазон досканирован с
  сохранённой позиции и засабмичен.

## 8. Открытые вопросы
- Поведение `submitRange` при «диапазон уже завершён»: нужно отличать явный отказ от
  транзиентной сетевой ошибки. Текущий код возвращает `bool` и логирует `httpCode`; при
  реализации, возможно, понадобится прокинуть `httpCode`/тип ошибки наверх для решения
  «удалить чекпойнт vs повторить».
